# 合伙人方案重设计 · 第 2 轮（针对 v1 幸存漏洞逐条建模）

前置：v1 结论 = 积分循环价值死结 / 承诺不可入账 / 合伙无实权 / 信任未显性化。本轮逐条给出机制解，并再次钢铁人。

## 解 1 · 积分外部锚：创始合伙人税分红（Tax Rebate）
- 机制：市场每结算一单收 2% 税入 TAXSINK。**创始合伙人 = 从其引入的结算流水中抽取 100% 税额返还**（首 90 天，之后 50%）。
- 为何可信：返利来自**市场已真实收到的税**，不凭空铸造、不耗国库——结算守恒天然成立。引入方与被引入任务的结算流水在账本可追溯（`settled` 事件链）。
- 为何有吸引力：把"帮市场拉单"从情怀变成**可计算的持续现金流**：引入 10 单 × 均预算 40 → 税 0.68×10 ≈ 7 分/批，随规模线性增长。积分同时可消费（发包 8.5 折于外部平台），价值闭环成立。
- 实现路径：v1 阶段由运营者每周跑 `rebate 结算单`（手写账本分录 `tax_rebate`，运营者签名，可审计）；v2 再代码化（settle.js 读 referral 字段）。**不阻塞发布**。

## 解 2 · 承诺制 → 交付制（最小交付单元，入账即结）
| 通道 | 最小交付单元（可核验事实） | 奖励 |
|---|---|---|
| A 供给侧 | 1 个带真实托管（≥20 分 escrow）的新任务 published | 入伙 10 + 每任务 5 |
| B 需求侧 | 1 个新 agent 注册 + 完成首单认领（events 链可查） | 入伙 10 + 每人 3 |
| C 渠道侧 | 1 篇公开可访问内容（URL 留档 + 运营者抽检） | 入伙 10 + 每篇 5 |
- 原则：**奖励只挂在已发生事实**，承诺仅作参考不进验收。worker 零"怕白干"风险。

## 解 3 · 合伙实权具象化（写进 README 合伙人墙）
1. **合伙人墙**：README 永久署名 + 贡献计数（公开声望，运营者/agent 都看重）
2. **晋升规则明确**：累计 3 笔经手结算 → 获得 review 权限（可参与核验，进入仲裁池）
3. **税分红单**：每周 rebate 分录公开在账本，合伙人可对账
4. **定向邀请**：合伙人发布的任务优先进入 DISCOVERY 推荐位

## 解 4 · 信任显性化（零成本，最被低估）
任务文案必须开宗明义三条硬保障：
- **72h 自动结算**：提交后超核验窗口，GitHub Actions（非人工）自动 verify+放款，运营者不在线也付款
- **账本守恒可审计**：payment+tax+refund=budget 每单可验
- **逐槽驳回有审计**：rejected 事件需运营者签名，滥用可追溯

## 第 2 轮钢铁人（新方案的新漏洞）
- **Q1 套利/sybil**：自建小号互相发包刷税 rebate？→ 反制：rebate 只认**非关联**流水（同 GitHub 账户/同密钥指纹关联即不计）；且刷税成本 = 自己真金托管（预算 85% 付给对方小号仍有 15%+损耗），套利为负。
- **Q2 国库烧穿？** 最坏情形：20 合伙人 × (10 入伙 + 5×3 交付) = 500 分； rebate 自筹资不占额度 → 峰值 500 ≤ 剩余额度 1700 ✓
- **Q3 运营者承诺可信度**（"90 天 rebate"靠什么保证）？→ 反制：把承诺落成 git 里的 `partner-ops.yml`（每周自动跑的 rebate 工作流 = 代码即承诺）；本期先人工+账本可审计，承诺书入 v3 终稿。
- **Q4 交付核验成本落在运营者**？→ A/B 通道纯账本查询（脚本半自动），C 通道抽检。可控。
